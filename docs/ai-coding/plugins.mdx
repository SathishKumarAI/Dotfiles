# Claude Code Plugins

**Intro.** Plugins bundle skills, agents, hooks, MCP servers, and LSP servers
behind one install. They are strictly more than skills — and they are **not
free**: every plugin adds always-on tokens to *every* session. This page is the
installed inventory with real measured costs, not estimates.

> **Snapshot:** 2026-07-31 (post-audit) · **31 installed, 10 enabled** ·
> **~6.9k tokens always-on**, down from ~20.9k · two marketplaces.
> Measure yours with `claude plugin details <name>`.

**Full audit + decision table + per-repo scoping guide:**
[`../PLUGIN-AUDIT.md`](../PLUGIN-AUDIT.md). That file is the working document;
this page is the reference.

## Scoping instead of deleting

The lever that makes a lean global set workable: a repo's own
`.claude/settings.json` takes the same `enabledPlugins` key and layers over the
user-level file, so you list only the deltas.

```json
{
  "enabledPlugins": {
    "huggingface-skills@claude-plugins-official": true
  }
}
```

Dropped in `~/coding/live/pickleball-vision-llm/`, that charges HF's 5k
always-on tokens **only** in that repo. Commit the file — the config travels
with the work. Use `.claude/settings.local.json` (gitignored) for anything
carrying a secret. Verify once with `/plugin` inside the repo versus outside.

There is no built-in "auto-disable after N days unused". Scoping is the
supported substitute.

**`posthog` was a bad trade** and is now disabled. 133 skills and 23.2k
always-on tokens for a product-analytics tool used occasionally - 53% of the
whole bill. Disabling it took the total from ~44.1k to **~20.9k**:

```bash
claude plugin disable posthog        # keeps it installed, stops the context cost
claude plugin enable posthog         # turn back on when you need it
```

The same logic applies to `firecrawl`, `pinecone`, and `huggingface-skills` if
you are not actively using them. `disable` is the right tool — no need to
uninstall and re-resolve later.

## Known issue — the `mlflow` hooks bug

`mlflow@1.0.0` ships a manifest that declares its own hooks file:

```json
"hooks": "./hooks/hooks.json"
```

Claude Code loads `hooks/hooks.json` **automatically**, so declaring it again is
a duplicate load and the entire plugin fails:

```
Status: ✘ failed to load
Error: Hook load failed: Duplicate hooks file detected: ./hooks/hooks.json
       resolves to already-loaded file ...
```

`manifest.hooks` should only reference *additional* hook files. Local fix —
delete that one line from the cached manifest:

```bash
f=~/.claude/plugins/cache/claude-plugins-official/mlflow/1.0.0/.claude-plugin/plugin.json
cp "$f" "$f.bak"
sed -i '/"hooks": ".\/hooks\/hooks.json",/d' "$f"
claude plugin list | grep -A3 mlflow    # verify: enabled
```

> **This patch is lost when the plugin updates.** It is a workaround for an
> upstream packaging bug, not a fix — re-apply after `claude plugin update
> mlflow`, or report it to `mlflow/skills`.

## Where the tokens actually go

Three separate cost sites. Only one of them responds to disabling, which is why
disabling is the lever that matters.

| Cost site | Charged | What lives there | Shrink it by |
|---|---|---|---|
| System prompt | **every message** | skill `description:` lines, agent descriptions, command names | disabling the plugin — nothing else touches it |
| Tool schemas | on load | MCP tool JSON schemas | already deferred on this machine (`ToolSearch` loads them on demand) |
| Hooks | per session or per message | hook script output injected as context | disable the plugin, or set its opt-out env var |

Agent descriptions cost more per item than skill descriptions — they ship full
multi-example blocks. `pr-review-toolkit` was 2,033 tokens from **six agents and
one skill**, which is why it outranked plugins with ten skills.

Hooks currently firing: `caveman` (SessionStart + UserPromptSubmit, every
message — but net-negative, output compression more than pays for it),
`superpowers` (SessionStart, re-injects the whole `using-superpowers` body,
~700 tokens — that is the design, it is what makes the skills fire reliably),
`mlflow` (UserPromptSubmit, every message).

## Rules of thumb

1. **Measure before you keep.** `claude plugin details <name>` before deciding a
   plugin earns its slot. A 133-skill plugin is a red flag.
2. **`disable`, don't uninstall.** Keeps it one command away at zero cost.
3. **Scope heavy plugins per repo** rather than keeping them global. See above.
4. **MCP-only plugins are near-free in context** — their cost is tool schemas,
   which load differently from skill frontmatter. They still cost *startup time*
   if they shell out to `npx`/`uvx`.
5. **A plugin whose auth was never set up is pure cost.** It cannot work, and
   you pay its context bill every message regardless. Audit for this first.
6. **Re-audit after every install.** The failure mode is drift — plugins
   accumulate, nobody removes them.
7. **Vetted only.** Same rule as skills: plugin path, never `curl|bash`. See
   [skills](./skills.mdx).
